# Chronicle: roadmap and decisions

A World Anvil-style worldbuilding notebook. Self-hosted, React frontend, Node + SQLite backend.

## Decisions (agreed)

| Topic | Decision |
|---|---|
| Auth | Username + password, session cookie (HttpOnly, SameSite=Lax, Secure in prod). Roles: `owner`, `editor`, `viewer` (read-only). Rate-limited login. |
| Storage | SQLite (WAL) via better-sqlite3. Images on disk in `data/uploads`. |
| Editing | Block-based documents (TipTap/ProseMirror). Last-write-wins; no CRDT yet. |
| Client cache | Workspace metadata and opened pages are cached in IndexedDB, so the app starts and reads offline. Offline *writes* are only retried while the page stays open. |
| Links | `{{Name}}`, `{{Name\|shown text}}`, `{{Name#Section}}`. Stored as page ids, so renames never break links. Unresolved links create the page on demand. |
| Workspaces | A workspace is a **world**. Cross-workspace copy: unresolved "ghost" links (A) plus a prompt to also copy linked pages (B). |
| Stat blocks | Template-driven (data in `web/src/editor/templates.ts`), no computed fields. 5e templates first. |
| Calendar | Custom: year, up to two optional named sub-levels (e.g. season, month), days. User-defined lengths, no leap years. |
| Themes | Picker only, 10 themes. CSS variables in `styles.css` + list in `themes.ts`. |

## Map and timeline (phase 3, built)

**Tiling.** Upload (PNG/JPEG/WebP/AVIF, up to 600 MB) is stored as `data/maps/<id>/source.<ext>`. A single-job background queue cuts it with sharp (`layout: 'google'`, 256px webp, transparent-padded edge tiles) into `tiles/<z>/<y>/<x>.webp`. Maps still `processing` at boot are resumed. Tiles are auth-gated and cached immutably. The client uses Leaflet `CRS.Simple`; image px <-> latlng goes through `project/unproject` at `maxZoom`.

**Data.** `maps` (nested via `parent_map_id`, `scale_m_per_px`), `map_layers`, `map_items` (point/line/polygon; `time_mode` static|timed|journey; `keyframes`; `journey`), `calendars` (one JSON per workspace), `events` (page_id optional, `t_start`, `t_end`).

**Time.** `T` is an integer day count. `web/src/lib/calendar.ts` converts to and from year / level1 / level2 / day. No leap years. Changing the calendar later keeps all dates as day counts.

**Items over time.**
- Timed items have keyframes `{t, geometry?, hidden?}`. Before the first keyframe the item is absent. `style.glide` interpolates between keyframes (polygons only when the vertex counts match).
- Journey lines have `waypoints[{arrive, depart}]`. Stops without a time are spread by distance between known ones. The travelled part is solid, the rest dashed, and a dot marks the position at T.
- A line is timed or a journey, never both (the server rejects it). Only lines can be journeys.

**UI.** Tools: select, marker, line, region, measure (with "use as scale"). Vertex handles (drag, click midpoint to add, double-click to remove). Layers panel, nested-map links and breadcrumbs, scale bar. Per-map time bar with play, step, jump-to-change, ticks and a calendar popup. Timeline view with a calendar editor. `/pin` and `/teven` on pages; the "Where & when" section lists a page's pins and events. Hovering an item with a linked page shows the normal preview card.

**Tests.** `scripts/smoke-maps.mjs` (API), `scripts/test-time.ts` (calendar and time math; bundle with esbuild, run with node). Seeders: `scripts/seed-map.mjs`, `scripts/seed-items.mjs`.

**Verified in the browser:** two-level calendar editor, measure + set scale, polygons, keyframes, layers, nested maps with breadcrumbs, phone-width layout, event editing.

## Relations (phase 4, built)
- Table `relations(source, target, kind parent|spouse|sibling|other, label)`. `parent` = source is the parent of target; spouse and sibling are symmetric and stored once; `other` is directed with a free label ("rival of"). The server rejects self links, duplicates, parent loops and pages from other worlds. Trashed pages hide their relations.
- `/relation` on a page opens a dialog (parent of / child of / married to / sibling of / custom). The page shows a "Relations" section with remove buttons (editors only).
- Sidebar "Relations" (also Ctrl+K `/relations`): family trees (layered layout in `web/src/lib/family.ts`, couples drawn as one block with a shared child line, pan/zoom, hover previews) and a free force-directed diagram for custom relations, optionally including family links.
- Tests: `scripts/smoke-relations.mjs`, `scripts/test-family.ts`; `scripts/seed-family.mjs` creates a demo family.
## Copy between worlds (built)
- Page menu, folder context menu (whole folder incl. subfolders) and Ctrl+K `/copy this page` open one dialog: pick the target world, see which pages are linked from the selection, optionally tick them to copy too (B). Linked pages are not followed recursively.
- Server (`server/src/routes/copy.ts`): `POST /api/copy/preview` and `POST /api/copy`, one transaction. New ids for every page; wikilink/embed ids inside the copied set are remapped, everything else becomes a **ghost link** that keeps its name (A) and connects automatically when a page with that name is created or copied later. Embeds of missing pages show a hint instead of a spinner.
- Also copied: tags, folder path (recreated by name), images and portraits (files duplicated, urls rewritten), relations between two copied pages. Not copied: map pins, timeline events, history.
- Title collisions are never merged: the copy becomes `Title (copy)`, `Title (copy 2)`.
- Tests: `scripts/smoke-copy.mjs` (22 checks).

## Sessions and statistics (built)
- Tables `game_sessions(number, title, played_on, t_start, t_end, page_id)` and `page_activity(page_id, day, written, net, created)`. Activity is recorded on page create, on every save (word delta) and on copy. Migration 4 backfills one row per existing page, dated on its creation day, so older worlds start with all their pages on one day.
- `written` counts growth only (typing), so deleting or tidying never lowers it. `net` keeps the signed change.
- A session owns the days from its own `played_on` until the next session's date: the game, the write-up and the prep for next time. Its stats (pages created, words written, pages touched) are summed over that range, so every page is counted in exactly one session. Moving a session's date moves the stats.
- `t_start` / `t_end` are optional in-world dates (calendar day counts, shown with `formatRange`).
- "New session" can create a write-up page: "Session N: title" in an auto-created "Sessions" folder, tag `session`, sections Recap, Decisions and consequences, Loose ends, Next session. Or attach an existing page, or none. Deleting a session keeps its page.
- Sidebar "Sessions" (Ctrl+K `/sessions`): statistics panel (last 30 days, all time or custom range; totals, per-day chart, most written pages) and the journal list. Viewers see everything but cannot add, edit or delete.
- API: `GET/POST /api/workspaces/:ws/sessions`, `PATCH/DELETE /api/sessions/:id`, `GET /api/workspaces/:ws/stats?from&to` (inclusive dates).
- Tests: `scripts/smoke-sessions.mjs` (30 checks).
- Verified in the browser: create with write-up page, edit, link to the page, live word count while typing, viewer read-only, phone width.

## Public sharing (built)
- Page `…` menu → "Share publicly…" creates an unguessable link `/s/<token>` (18 random bytes). One token per page; stopping deletes it for good, sharing again makes a new one. Editors and owners only; viewers cannot share. Settings lists all shared pages with copy/stop.
- Server (`server/src/routes/shares.ts`, table `shares`): `GET /api/public/:token` and `GET /api/public/img/:id` are the only unauthenticated routes (rate limited, 120/min). The page document is rewritten before it leaves the server (`publicDoc`):
  - links to shared pages become ordinary links to `/s/<their token>`; links to anything else become plain text, so private titles and ids never leak (the alias or name typed in the link is kept)
  - embeds of shared pages are inlined (section embeds only that section, one level deep); embeds of unshared pages are dropped
  - images are rewritten to `/api/public/img/<id>`, which only serves an upload while a currently shared page uses it
  - map pins, relations, backlinks, tags, search and the rest of the world are not exposed at all
- Client: `/s/:token` is routed in `main.tsx` before `App`, so no login, store or sidebar loads. Read-only render of the same editor nodes (stat blocks included). Unknown or revoked tokens show a neutral "not shared" page.
- Tests: `scripts/smoke-share.mjs` (33 checks, mostly about what must not leak).

## Export and restore (built)
- **Export this world** (Settings, any logged-in user): `GET /api/workspaces/:ws/export` streams a zip.
  - `pages/<folders>/<Title>.md`: front-matter (title, icon, aliases, tags, created, updated, id), then the page as Markdown. Links are `[[Page]]`, `[[Page#Section|shown]]`, embeds `![[Page]]` (using the page's current title), stat blocks a fenced ```` ```statblock <template> ```` block of `key: value` lines, images relative links into `images/`. Names are sanitised; duplicate titles get ` (2)`. Trashed pages are left out.
  - `world.json`: the lossless version (editor documents, folders, tags, relations, events, sessions, zettels, calendar, maps with layers and pins, upload list).
  - `images/` and `maps/<id>/source.*` (original map images; tiles are not exported, they are rebuilt from the source).
- **Backups** (owner, Settings): daily snapshots (newest 14, `BACKUP_KEEP`), list with size and kind, download, delete, "Back up now".
- **Restore**: `POST /api/backups/:name/restore`. It first writes a `pre-restore-*` snapshot (newest 5 kept), then copies every content table from the chosen snapshot into the live database in one transaction. The snapshot is migrated to the current schema first; a newer-schema backup is refused; a failed foreign-key check rolls everything back. **Accounts and logins are never touched**, so nobody is logged out and an account created after the backup survives. Undo a restore by restoring the `pre-restore` snapshot.
- **Download everything** (owner): `GET /api/export/full`, a zip with a consistent `dnd.db` snapshot, `uploads/` and map sources. Moving to a new machine = unzip into the data directory.
- Snapshots contain only the database; uploads and map sources are not in them. Restoring an old snapshot keeps the current files, so images referenced by the backup still exist (files are never deleted by a restore).
- The zip writer is `server/src/zip.ts` (no dependency, streams entry by entry, no zip64, 4 GB limit). Markdown conversion is `server/src/markdown.ts`.
- Tests: `scripts/smoke-export.mjs` (35 checks; reads the zip with an independent reader and verifies CRCs).

## Electron (built)
- `electron/` is a separate package (not in the root workspaces, so the Docker build never downloads Electron). It is a thin window onto the server, not a copy of the web app: one codebase, and desktop and browser always agree.
- First start asks for the server address and checks it is a Chronicle server (`/api/auth/me` answers JSON 200/401) before saving it in `userData/settings.json`. `CHRONICLE_URL` overrides it.
- Multi-window: `Ctrl+Shift+N` or launching again opens another window on the same server. Windows share the cookie jar, so one login. Cookies are flushed on quit so the login survives.
- Links to anything but the server open in the system browser. Sandbox on, context isolation on, no Node in the page. The `connect` bridge only exists on the local `file:` page and is also refused by sender URL in the main process.
- No menu bar, so nothing steals the app's `Alt+…` or `Ctrl+K` shortcuts (AltGr on a German keyboard stays safe). The few desktop keys are in `electron/README.md`.
- Packaging with electron-builder (`npm run dist:win` etc.); the icon comes from `web/public/icon.svg`. `dist:win` was run: the NSIS installer (97 MB) and the portable exe (89 MB) build, and the portable exe starts and opens its window (the installer itself was not run).
- Tests: `scripts/test-electron.mjs <server> [user] [password]` launches the real app and drives it over the DevTools protocol (14 checks: loading, setup validation, remembered address, second window, login persistence, bridge not exposed to the server page).
- **Auto-update (0.2.0):** `electron/update.js` checks the latest GitHub release (public repo, no token) 8 s after start and every 6 h; `Ctrl+Shift+U`, the address screen button or the button in Settings ("Desktop app") checks on demand. The Settings button works without a bridge: the app puts `ChronicleDesktop/1` in the user agent and recognises `window.open('chronicle-desktop://check-updates')`; see `electron/README.md`. Installed (NSIS) builds use `electron-updater` with `latest.yml`. Portable builds cannot be replaced by it, so the app downloads the `*-portable.exe` asset beside itself, verifies size, SHA-256 (GitHub's asset `digest`) and the `MZ` header, and a temporary batch file swaps it in after quit. "Skip this version" is kept in `settings.json`. Pure helpers are in `electron/update-logic.js`.
- **Releases:** the Release workflow (`.github/workflows/release.yml`) runs `scripts/release.mjs`; if there are `feat:`/`fix:` commits since the last `vX.Y.Z` tag it sets the version in all four `package.json` files and both lockfiles, prepends a `CHANGELOG.md` section from the commit subjects, commits it, tags `vX.Y.Z` and pushes both in one push. The tag runs `.github/workflows/release-desktop.yml`, which publishes `Chronicle-Setup-X.Y.Z.exe`, `Chronicle-X.Y.Z-portable.exe`, `latest.yml` and the blockmap. Those names are a contract with the updater. The release notes are that version's `CHANGELOG.md` section; `scripts/extract-release-notes.mjs` (CRLF-safe, Windows checkouts) writes it to `electron/release-notes.md` (the GitHub release body, read by the portable app's dialog) and `electron/build/release-notes.md` (the `releaseNotes` field of `latest.yml`, read by the installed app's dialog), and `scripts/publish-release.mjs` creates the release with the notes before the build so electron-builder only uploads assets.
- Tests: `scripts/test-update-logic.mjs` (22 checks) and `scripts/test-update-flow.mjs` (15 checks; real Electron against a fake GitHub API, including the real exe swap).
- Not done: offline mode, code signing; the Linux and Mac targets are untested. The 0.1.0 builds have no updater, so they must be replaced by hand once. The updater was tested against a fake API, not yet against a real published release.

## Todos (built)
- `/todo` inserts an inline marker (TipTap atom node `todo` with `message`, `done`, `id`) and focuses its message field. Enter or Escape confirms, an empty message removes the marker. The old checkbox list is now `/checklist`.
- Table `todos` (migration 7) is an index rebuilt from the page document inside `reindexLinks`, so every save path (editor, restore, copy, version restore) keeps it in step. Todo text is not part of page text or word count.
- A todo that is ticked disappears from the page (the node stays in the document with `done: true`). It comes back when unticked in the Todos tab, and "Go to" on a done todo shows it briefly.
- Sidebar "Todos" (badge = open count, `Alt+T`, Ctrl+K "Open todos"): filter open/done/all and by text, grouped by page, with the paragraph around the marker as context. Tick, edit, delete, and "Go to" opens the page scrolled to the marker with a highlight.
- Changes from the tab go through `applyContent` on the server and over `todoBus` into an open editor (split view), so the editor's next autosave cannot undo them.
- Public shares drop todos. Markdown export writes `**TODO:** text` / `**DONE:** ~~text~~`; `world.json` keeps the node.
- API: `GET /api/workspaces/:ws/todos`, `PATCH|DELETE /api/pages/:id/todos/:todoId` (editors). Tests: `scripts/smoke-todos.mjs` (38 checks).

### Starter todo (built)
- Every new page gets a todo with the world's default text (`Fill me` unless changed). In a blank page it is the only line; when a template or captured text supplied content, it is appended after it. An empty text in the settings turns it off.
- Stored per world in `workspaces.settings` (JSON, migration 11; `newPageTodo`), edited under Settings, Worlds. `PATCH /api/workspaces/:id` takes `name` and/or `settings`; `GET /api/workspaces` returns the settings. Added server-side in `POST /api/workspaces/:ws/pages`, so quick capture, wikilink stubs and templates all get it.
- Pages created by other routes (copy between worlds, session notes, import) do not get a starter todo.

### Deleting a world (built)
- Settings, Worlds, "Delete this world" (confirm dialog, then the app switches to another world or the first-world prompt). `DELETE /api/workspaces/:id` is a soft delete (`deleted_at`): the rows stay in the database but the world disappears from lists, its bootstrap answers 404 and its public share links stop working. There is no undelete in the UI.

## Templates (built)
- Custom templates per world: sidebar "Templates" (Ctrl+K "Open templates"), or a page's `…` menu "Save as template…". Type `/template-name` in any page to insert the template at the cursor, in place of the typed text. Template items come before built-in commands in the slash menu.
- Table `templates` (migration 8): `name`, `slug` (lower case, letters and digits joined by hyphens), `description`, `content` (TipTap JSON). The slug is unique per world (409 on a clash).
- Heading and todo ids are stripped and todos reset to open on every save. Insertion gets fresh ids.
- Templates ride in the bootstrap, so the slash menu needs no request. `world.json` includes them, and backup restore brings them back.
- Editors and owners create, edit and delete; viewers can read only.
- API: `POST /api/workspaces/:ws/templates`, `PATCH|DELETE /api/templates/:id`. Tests: `scripts/smoke-templates.mjs` (29 checks).

## Slash chains (built)

What it does: the slash menu understands short chains in the style of Emmet, so `/h2{Plot hooks}+ul>li*3` inserts a heading and a three item list in one step.

- **Syntax.** `a>b` puts b inside a, `a+b` puts b after a (after `>`, a `+` stays inside the nest, as in Emmet: `ul>li+li` is a list of two). `a*3` repeats, `(a+b)*3` repeats a group, `a{text}` sets the text; text may hold spaces. In text `$` is the number of the repeat (`$$` pads to two digits), `\$` and `\}` are literal. Order of `{}` and `*` after a name does not matter. A leaf block that gets children places them after itself, so `h2{Hooks}>ul>li*3` works like `h2{Hooks}+ul>li*3`.
- **Blocks.** `h1` to `h4`, `p`, `ul`, `ol`, `task` (checklist), `li`, `quote`, `code`, `hr`, `todo`, `table` (`table3x4` is 3 rows by 4 columns, with a header row), plus the names of the slash menu (`bullet`, `number`, `checklist`, `divider`, `text`). The world's templates (`npc`) and stat blocks (`stat-5e-monster`) can be chained by their slash name. Dialog commands (`image`, `embed`, `pin`, `teven`, `relation`) may end a chain: everything before is inserted, then the dialog opens.
- **In the menu.** A query with an operator (or a table size) is a chain; any other query is a normal command search. A chain shows one entry that says what it will insert ("Heading 2, Bullet list (3 items)"). While it is not valid the entry is greyed with the reason, and the name being typed is offered as a completion (`ul>l` offers `ul>li`). Enter or Tab inserts; one undo removes the whole chain. "Chain blocks" in the menu types an example to start from.
- **More blocks.** `callout` (also `note`, `info`), `warning` (`warn`), `aloud`, `secret`, `fold{Title}`, `cols` (`cols3`, or `cols>col*3`; 2 to 4 columns), `col`, `toc`, `date`, `roll` (`roll20`: a table with one row per face of d4, d6, d8, d10, d12 or d20), and the presets `npc`, `place` and `encounter`. A preset is itself a chain (`PRESETS` in `chain.ts`) and sits below the world's own templates: a template called `npc` wins. All of them are also plain slash commands.
- **Limits.** 50 repeats, 300 blocks per chain, tables up to 20 by 20.
- **Code.** `web/src/editor/chain.ts` (pure: parser and expansion to TipTap JSON), `slash.ts` (menu wiring), `suggest.ts` (`disabled` items). The slash plugin now allows spaces in its query; a query with a space that is not a chain shows nothing, as before.
- **Tests.** `scripts/test-chain.ts` (bundle with esbuild, run with node).
- **Not done.** No custom named chains (templates cover that), no `^` to climb up a level, no inline formatting or links inside `{text}`.

## Manual (built)

What it does: a built-in manual explains the app, and a bare `/` in a page now lists every command.

- **Slash menu.** An empty query returns all commands in declared order (templates first, then built-in commands, then stat blocks); the popup scrolls. A typed query still shows the best 12. `/help` opens the manual. A chain with text after `>` and a space (`h2>My heading`) now says "Text goes in braces, e.g. h2{My heading}" instead of an unexpected-character error.
- **Manual view.** `{ type: 'manual' }`, `components/Manual.tsx`. Opened from the question mark button in the sidebar footer, `/help` in a page or "Open manual" in Ctrl+K. It has a search box and a contents row. The command table is built from `COMMAND_LIST` in `slash.ts`, the chain block names from `CHAIN_TAGS` in `chain.ts` and the shortcuts from `keys.ts`, so they follow the code. The prose is written by hand: update it when a feature changes.
- **Tests.** `scripts/test-chain.ts` covers the new chain message. The view has no server part.

## Comments (built)

What it does: typing `@` and a name in a page leaves a comment for that person. They find it in the Comments view, with a count in the sidebar, until they resolve it.

- **In the page.** An inline atom node `comment` with attributes `id`, `to` (username), `from` (username of the writer), `message`, `done`. `web/src/editor/Comment.tsx` (node view, like the todo marker) and `mention.ts` (the `@` suggestion; it offers everyone from `GET /api/workspaces/:ws/people`, which is the owners plus the world's members, cached for a minute). `@` only triggers after a space or at a line start, so addresses are left alone. UniqueID gives each comment an id.
- **Index.** Table `comments` (migration #15) is rebuilt from the page document on every save in `reindexLinks`, next to the todo index, and keeps `created_at` and `done_at` of known comments. It is derived data, so it is not backed up, copied or exported separately.
- **API.** `GET /api/workspaces/:ws/comments`, `GET /api/workspaces/:ws/people`, `PATCH|DELETE /api/pages/:id/comments/:commentId` (editors; `done`, `message`). Changes go through the live document when the page is open (`editTodoLive` with the node type), otherwise through `replaceContent`.
- **View.** Sidebar "Comments" (Ctrl+K "Open comments"): For me, From me, Everyone, with Open, Resolved, All and a text filter. The sidebar count is the open comments addressed to the signed-in account and follows page saves live. "Go to" opens the page and flashes the comment.
- **Privacy.** `publicDoc` drops comments from shared pages and embeds, `templateDoc` leaves them out of templates, and they are not part of the page text, outline or search. Markdown export writes `**Comment for @name:** text` (owner only).
- **Limits.** `from` is written by the client, so it is a label, not proof of who wrote it. There is no notification beyond the count, no threads or replies, and a comment is tied to a spot in the text, not to a selection. Copying a page to another world keeps its comments, even for people who are not in that world.
- **Tests.** `node scripts/smoke-comments.mjs <url> <user> <pass>`.

## Boxes, sections and columns (built)

What it does: new kinds of block for page layout, inserted from the slash menu or a chain (see "Slash chains"). `web/src/editor/blocks.tsx`.

- **Callout** (`callout`, attribute `kind`: `info`, `warning`, `aloud`, `secret`): a box that holds blocks. Click its label to switch the kind. A **secret** is for the GM: in a shared page its text is never sent. The reader sees a closed box saying "This is a secret. It stays closed in shared pages." A secret inside a fold, or inside an embedded page, is replaced the same way (`publicDoc` in `server/src/routes/shares.ts`).
- **Fold** (`fold`, attribute `title`): a titled section that holds blocks and can be closed. Open while writing, closed for readers; whether it is open is a view setting and not saved in the page.
- **Columns** (`columns` holding 2 to 4 `column`s): side by side, stacking on a narrow screen.
- **Contents** (`toc`): links to the headings of the page, kept current while typing. It has no data of its own.
- **Markdown export.** Callouts become a quote with a bold label (`> **Warning**`), secrets included because the export is the owner's. Folds become `<details><summary>`. Columns are written one after another, contents are left out.
- **Live editing, templates, copy and history** need nothing special: the live document conversion and the stored JSON are generic.
- **Known limitation.** The public library route (`/api/public/library/:key`) decides whether an entry is "linked by a shared page" from the page's raw stored text, so a library link that sits only inside a secret still makes that entry readable through the share. The entry is public Open5e data and the key has to be guessed.
- **Tests.** `scripts/smoke-blocks.mjs` (storage, secrets in shared pages and embeds, export), `scripts/test-chain.ts` (the chains).

## Special pages (built)
- A special page is a normal page with a fixed layout next to its text and an automatic tag. Built-in types: Person, Monster, Location. Custom types are per world and can be created, duplicated and deleted. Deleting a type makes its pages plain pages (the text and field values are kept).
- Layout: four zones (top, side, main, bottom), columns side-left / side-right / single (with one column, side blocks merge into main), side width in px (160 to 520). `flow: wrap` lets the text run on underneath the side column once its blocks end (the side floats); `flow: columns` keeps the text in its own column, and `sticky: true` then keeps the side in view while a long text scrolls. Person, Monster and Location use `wrap`; layouts saved before the option exist keep `columns`. On phones the side stacks above the text either way. Blocks: image (key, shape square/circle/wide/tall), statblock (any stat block form), fields (labelled key/value pairs, optionally long text), body (the normal page text). An image with the key `portrait` doubles as the page thumbnail.
- Data: `page_types` (migration 9): `name`, `icon` (curated lucide set in `TypeIcon.tsx`), `tag` (cleaned server-side, added to every page of the type), `source` (the layout as JSON, YAML or Markdown front matter) and `definition` (the normalized layout). Pages carry `props.type` (type id, so renames never break it) and `props.data` (field and stat block values, keyed by the layout keys).
- The layout is interpreted by the client (`web/src/lib/pageTypes.ts`: `parseSource`, `normalizeLayout`, `layoutToSource`, `resolveTypes`, `typeOf`); the server only stores it within size limits.
- UI: the sidebar "New special page" menu creates a page of a chosen type; the sidebar "Special pages" lists the types with their page counts. The type editor has a **Designer** (column setup, add, move between zones, reorder and remove blocks in each zone, per-block and field settings) and a **Source** tab (JSON, YAML or Markdown front matter), both with a live preview you can type in. A key used twice or left empty blocks saving. Built-in types are read-only; Duplicate makes an editable copy.
- Stat block forms have a `look` next to their sections (`style` classic / card / plain, `accent` colour, `font`, `width`, `columns`), stored in `stat_templates.definition` beside `sections` and edited in the form designer or its source. Section kinds added: `abilities` (six scores with modifiers, `layout` row or table with optional save column; values under `str`..`cha` and `str_save`..) and `columns: 2` on `rows`. Text areas render `***Name.***`, `**bold**` and `*italic*` when previewed. The built-in monster and player forms use the classic look; "5e Monster (2024 layout)" is new. Forms saved before this have no look and keep the card style. Tests: `scripts/smoke-worlds.mjs`.
- Rides in the bootstrap (and the IndexedDB cache) and in `world.json` / backup restore. Copying between worlds does not carry custom page types: their pages become plain pages, while stat block forms are matched by name.
- API: `POST /api/workspaces/:ws/page-types`, `PATCH|DELETE /api/page-types/:id` (editors and owners; viewers read only). Tests: `scripts/smoke-pagetypes.mjs` (11 checks), `scripts/test-layout.ts` (parse/serialize round trip, key handling; 16 checks).

## Creature sheet (built)

What it does: a Monster page shows and edits its creature as a real sheet instead of a text form. Numbers are numbers (armor class, hit points, speeds, abilities, saves, skills, senses, challenge rating), modifiers, passive Perception and proficiency bonus are worked out and never typed twice, and traits, actions, bonus actions, reactions and legendary actions are separate entries with their own recharge, uses per day or cost.

- **Data.** `props.sheet`, described in `web/src/lib/sheet.ts` and validated by `server/src/sheet.ts`. Edits go through `propsPatch.sheet` (field paths such as `hp.max`), so two people editing different fields do not overwrite each other. Library imports of creatures write the sheet.
- **Old pages.** A Monster page with only the old text stat block (`props.data.main`) is converted for display and stored as a sheet on its first edit. "Edit as text form" under the sheet switches back to the old form; changing the old form drops the stored sheet, so the two never disagree.
- **Where.** The Monster page (`web/src/components/SheetView.tsx`, used by `TypeLayout`), and in the tabletop panel as a card with roll buttons. Read-only viewers see the printed stat block with library terms linked. The Library view and hover previews still draw the older stat block.
- **Characters.** A Person page offers "Add a character sheet". It is the same sheet with `kind: "character"` and what a player tracks: name, player, species, background, alignment, classes with levels and subclass (multiclass adds up), inspiration, XP, armor class, speed, hit points (current, maximum, temporary) and hit dice, death saves, the six abilities, saving throw and skill proficiency (click the mark to cycle none, proficient, expertise), other proficiencies and languages, spellcasting ability with save DC and spell attack, spell slots by level (click circles to spend them), spells, attacks, features and traits, equipment with quantity and "equipped", and coins. Proficiency bonus follows the total level; saves, skills, passive Perception, initiative and spell numbers are worked out. "Long rest" restores hit points, clears temporary ones, refills slots, returns half the hit dice (at least one) and clears death saves. Read-only viewers see the same sheet without controls. At the table, a token linked to a character takes its current and maximum hit points from the sheet, the card rolls saves and every skill with the proficiencies applied, and damage or healing on the token is written back to the sheet's current hit points (`followHp` in `server/src/table.ts`).
- **Not done yet.** Removing a character sheet again, rolling from the page itself (the roll buttons are on the table card), spell and item pickers from the Library, the same sheet in hover previews and the Library view, 2024 species and background rules, custom stat block forms.
- **Tests.** `scripts/test-sheet.ts` (derived numbers, rests), `scripts/smoke-sheet.mjs`, `scripts/smoke-table.mjs` (hit points follow the token), `e2e/tests/content.spec.ts` (creature and character sheets).

## Rules systems: D&D 5e 2014, 2024 and Pathfinder 2e (built, first steps)

A world plays by one set of rules: Settings, Worlds, **Rules** (`workspaces.settings.system`, `5e`, `5e-2024` or `pf2e`, default 2014; any editor of the world can change it). What it decides today:

- **Encounter difficulty.** 2014: the creatures' XP times a multiplier for how many there are, against easy, medium, hard and deadly thresholds. 2024: no multiplier; the creatures' XP is compared with the party's budget (XP per character, summed) at Low, Moderate and High, and anything above High is flagged as more than the party should face. The budget table is in `web/src/tabletop/encounter.ts`. Levels 1, 3, 5, 10 and 20 were checked against the published table; the other rows are from the book as remembered, so check them before relying on them at the table.
- **New character sheets** start with the world's ruleset, and the sheet says "Heroic Inspiration" instead of "Inspiration" under 2024. Creature sheets already carry their own ruleset (a 2024 creature shows the 2024 stat block layout).
- **Pathfinder 2e** is the third choice. What it changes:
  - **Encounter threat.** Each creature is worth XP by how far its level is from the party's (level -4: 10, -3: 15, -2: 20, -1: 30, equal: 40, +1: 60, +2: 80, +3: 120, +4: 160; weaker than four levels below counts for nothing). The party level is the rounded average. The total is a threat level against budgets for four characters (Trivial 40, Low 60, Moderate 80, Severe 120, Extreme 160), each character more or fewer adding or taking away 10, 15, 20, 30 and 40 (`web/src/tabletop/encounter.ts`). Hazards are not counted. A creature without a Pathfinder sheet counts as the party's level.
  - **Creature sheet.** A Monster page in a Pathfinder world offers "Use a Pathfinder 2e sheet": level, rarity and traits, Perception, skills, the six ability modifiers (modifiers, not scores), AC, Fortitude, Reflex and Will, hit points, speeds, immunities, resistances, weaknesses, abilities, strikes and reactions with their action cost (one, two, three, reaction, free), attack bonus, damage and "agile". Same storage and in place editing as the 5e sheet (`props.sheet.pf2e`, `web/src/components/Pf2eSheet.tsx`).
  - **At the table.** Initiative is rolled with Perception. The roll card has Perception, the three saves, skills, and for every strike three buttons for the first, second and third attack with the multiple attack penalty (-5 and -10, or -4 and -8 for agile). Conditions are the Pathfinder list; those with a value (Frightened 2) go up by one on each click and clear after 4.
  - **Degrees of success.** Write "dc 25" in a roll's label (`/roll 1d20+12 Athletics dc 25`) and the chat says how it went: critical success at 10 or more over, success, failure, critical failure at 10 or more under, moved one step by a natural 20 or 1. In a 5e world the same label gives success or failure.
  - **Characters.** A Person page in a Pathfinder world offers "Add a character sheet" (`web/src/components/Pf2eCharacterSheet.tsx`). You enter the level, the six ability modifiers and a proficiency rank (U, T, E, M, L: click the letter to change it) for Perception, the three saves, class DC, spell proficiency, armor, the sixteen skills, lore skills and each strike; the sheet works out the rest: level plus two per rank (nothing when untrained) plus the modifier. Armor class is 10, plus Dexterity up to the armor's cap, plus the armor bonus, armor proficiency and anything else. Strikes show the first, second and third attack with the multiple attack penalty and their damage. Also on the sheet: ancestry, heritage, background, class and key ability, XP, hero points, hit points with temporary points, dying and wounded, speed, spellcasting tradition and ability with spell DC and attack, focus points, spell slots for ranks 1 to 10 (click circles to spend them), feats and actions with action costs, equipment and coins. **Rest** heals Constitution times level hit points and returns spell slots. Perception, saves and armor class are written back to the sheet with every edit, so initiative, the token's armor class and the roll card always agree with the ranks. At the table the card rolls Perception, saves, every skill and lore, and each strike with its three attack buttons; hit points follow the token as for 5e characters.
  - **Not done yet.** Ancestry and class feature lists, spell lists with heightening, persistent damage, importing creatures from a library (the Library is the 5e Open5e data; no Pathfinder content is bundled, you enter what your table owns), a level-up helper. 5e character sheets are not offered in a Pathfinder world.
- **Not done yet (5e 2024).** Species and background rules, weapon mastery, 2024 exhaustion, 2024 class features. A system is still a setting plus a few branches, not a loadable pack; that format comes when a fourth system needs it.
- **Tests.** `scripts/test-encounter.ts`, `scripts/smoke-worlds.mjs`, `e2e/tests/tabletop.spec.ts` (2024 rules).

## Library (Open5e, built)

A read-only reference library of everything Open5e publishes (api.open5e.com/v2): creatures, magic items, equipment (weapons and armor are part of it), spells, classes and subclasses, species, backgrounds, feats and conditions. It belongs to the server, not to a world, and is opened at any time from the sidebar ("Library") or the command list.

**Decisions.**
- Own SQLite file `DATA_DIR/library.db`. It is reference data that can be downloaded again, so backups, restore, export and world copies leave it out.
- The owner downloads it once with a button ("Download the library", about a minute, 20 MB) and can refresh it later. Nothing is downloaded automatically.
- Each entry exists once. When several books have the same name, the newest edition of the rules wins (2024, then 2014, then others), then the official SRD over third-party books, then the newest publication date. Older versions cannot be picked. Classes and species also compare their parent, so subclasses of different classes stay apart.
- Entry ids are `<category>:<open5e key>` because Open5e keys repeat across categories (`srd-2024_camel` is both a creature and a mount).
- Every refresh appends `CREATED`, `UPDATED` and `DELETED` lines (timestamp, category, id, name) to `DATA_DIR/library.log`. There is no screen for it.

**Quick add.** Alt+L (or "Add from the library" in the command list) opens a palette. Names are matched with the same fuzzy search as the page search, in the browser, over a compact index (about 6,300 rows) that is cached in IndexedDB per library version. Enter adds the entry to the current world and opens it, Shift+Enter opens it in the Library view. Creatures become a Monster page with the stat block filled in, everything else becomes a normal page with the text as the body and the source and license at the end.

**Mapping.** `web/src/lib/open5e.ts`. Creatures fill the built-in 5e monster form (classic or 2024 layout, by the source book's ruleset). Action text is taken from each action's `desc` and not from Open5e's structured attack data, which has mistakes (a goblin's scimitar listed as thunder damage). Speed uses the printed values, not the padded `speed_all`. Everything else goes through `entryText`: a subtitle, labelled facts and titled sections.

**API.** `GET /api/library/status`, `GET /api/library/index`, `GET /api/library/entries/:id` (any signed-in user), `POST /api/library/refresh` (owner, runs in the background, the client polls the status). Tests: `node scripts/smoke-library.mjs <url> gm <password>` (needs internet).

**Links to library entries (phase 2).**
- Typing `{{` shows library entries under "Library" after the pages (from two letters on, five at most, source and kind shown). Picking one inserts a wikilink with the attribute `libKey` (the entry id) and no page. It is drawn with a dotted underline and opens the entry in the Library view (Ctrl for a new tab, Shift for the split view). Entries already imported into the world are left out of the popup because their page shows up instead.
- `links.lib_key` (migration 12) holds these links; `target_id` stays empty and they are never matched by name, so a page called "Goblin" does not capture a link to the library Goblin, and they are not counted as missing pages or ghosts when copying.
- The Library view lists "Linked from": pages of the current world that link to the entry. Links are per world, the library is global.
- Importing sets `props.library` on the page, so an entry becomes a page only once per world (the button then reads "Open the page"). If pages link to the entry, a dialog asks whether to point those links at the new page. `POST /api/workspaces/:ws/library-links/repoint` rewrites the link nodes (keeping a differing shown text as the alias) and reindexes the pages like a normal save.
- Public pages: a library link on a shared page is a link to `/s/<token>?lib=<id>`, which shows the entry read-only. `GET /api/public/library/:id` answers only for entries that a shared page links to, so the library is not browsable. Markdown export writes a library link as plain text.

**Linked fields (phase 3).**
- A field of a special page can be a link to library entries of one kind: species, class, background, feat, spell, magic item, equipment, creature or condition. In the designer the field's type reads "Link: class" and so on, with "Several" for lists such as spells. In the YAML source: `{ key: class, label: Class, library: class }` and `{ key: spells, label: Spells, library: spell, multi: true }`.
- The value is a list of entries `{ name, libKey?, pageId? }` in `props.data`. Typing offers the pages of the world that were imported from that kind first, then library entries (imported ones are left out), and "Use “…” as text" for homebrew. Entries open the library entry or the page; ctrl and shift work as for links in text. Older plain-text values show as one unlinked entry and are replaced when the field is edited.
- Field entries go into the same link index as links in the text (`links.lib_key` for library entries, `target_id` for pages), so "Linked from", the graph and backlinks include them. The index is rebuilt on every save, also when only the fields changed. The repoint after an import rewrites field entries too. Copying a page to another world keeps library entries and turns entries that point at a page left behind into plain text.
- The built-in Person page uses it for Race (species) and Class / Role (class).
**Every kind has its own page (phase 4).**
- Importing an entry makes a page of the matching built-in special page type, with the data in its fields or stat block and the text in the body: creatures become Monster (5e Monster or 2024 form), spells Spell (5e Spell form), equipment and magic items Item (5e Item form), classes Class, species Species, backgrounds Background, feats Feat, conditions Condition. Each type adds its own tag. The library view shows spells and items in the same forms.
- Classes carry hit die, saving throws, primary ability and the parent class of a subclass (a link) in the side fields. The body holds the core traits table, proficiencies and equipment, a level progression table (proficiency bonus, class columns such as rages or cantrips, spell slots, features gained) and every feature with its levels. Species link their parent species. Feats show kind and prerequisite. A condition keeps only the wording of its own book.
- Text from the data set keeps its structure: bullet lists, tables, bold and italic become real editor content.
- Stat block forms can hold links. A field of type `link` (designer: "Link: class" and so on, "Allow several entries"; source: `{ key: classes, label: Class, type: link, library: class, multi: true }`) works like a linked page field. The stat block data stays plain strings: the shown text lives under the field's key, the links as JSON under `<key>:refs`. The server reads these (`server/src/refs.ts`) for the link index, the repoint after an import and copying between worlds; shared pages keep the text and drop the links; Markdown export leaves the `:refs` lines out.
- The 5e Spell form links its classes. The 5e Player Character form got Species, Class, Background, Feats and Spells as links.
- Not done: a class page does not list its spells (Open5e stores the classes on each spell, not the spells on each class).

**Terms and properties (phase 5).**
- Open5e publishes what other entries refer to as entries of their own, and the library holds them: weapon properties (`weaponproperties`, with the full explanation), damage types, skills, abilities, spell schools, languages, creature types, alignments, sizes and the rules text (`rules`, about 280 entries). They are searched, opened and linked like everything else, and importing one makes a Rule page (kind, section and a few details as fields, the text as the body).
- Links: an item's damage type and weapon properties, a spell's school, and a creature's size, type and alignment are links. Weapon properties keep their detail next to the link ("Versatile (1d10)"): an entry has a `note` besides its name, so the detail survives when the link is moved to an imported page. A Monster page has a "Classification" block for size, type and alignment.
- Rules that share a name (Ability Checks appears in several sections) are separate entries; the section shows next to the name. Alignments have no name in Open5e and get one from their key.
- Not linked: a creature's skills, languages, resistances and condition immunities stay text, because they carry numbers or qualifiers ("Stealth +6", "nonmagical attacks") that a linked entry cannot hold when typed by hand. Item categories, rarities and environments have no explanation text in Open5e and stay text.
- Existing libraries have to be refreshed once (Library, Refresh) to download the new kinds.

**Names in text link to their entries (phase 6).**
- The names of library entries inside running text are links: "Charisma" in a class, a prone creature, *Fireball* in a feature, fire damage in a trait. `web/src/lib/autolink.ts` finds them (tested by `scripts/test-autolink.ts`).
- Where: the Library view (sections, tables, facts and the text fields of spell, item and creature stat blocks), the text fields of stat blocks on pages when read (shown as links, nothing stored, and to the imported page where the entry was imported), and the body of a page when it is imported (stored as links, so backlinks and the repoint after an import work). The page menu has "Link library terms" for pages that already exist. Shared pages show plain text.
- Rules, so that ordinary words stay plain: abilities, skills, classes, species, languages, items, feats and rules are linked only with the entry's capitals (Charisma, not charisma); conditions in any case (invisible needs a capital); spells only in italics, which is how the data writes them; damage types only before "damage" (fire damage); spell schools only before "spell" or "school"; weapon properties, creatures, creature types, alignments and sizes are not linked in text. Very short or common names (Common, Light, Shield, Range), items under five letters, single word feats under seven and single word rules under eight are skipped, and a one word rule at the end of a capitalised phrase (Weapon Proficiencies) is not cut out of it.
- Each entry is linked once per section (once per field in a stat block); headings, code and existing links are left alone; an entry never links to itself.
- Hover cards: resting the mouse on a link to a library entry (a name in text, a chip in a linked field, a library link in a page) shows a card like the one for page links: the stat block for creatures, spells and items, else the facts and the start of the text. Clicking the card opens the entry. Links inside a card do not open further cards. The card is placed from the link's position when it opens; if the list was redrawn in the meantime (a page opened, links refreshed) the link is gone and no card opens, and a card whose link disappears closes by itself (before, it could land in the top left corner and stay there, covering "New page").
- A class page's saving throws and primary ability are linked fields (ability). Pages imported before this change keep their text; "Link library terms" adds the links.

## Several people at once (built)

What it does: more than one person works in the same Chronicle at the same time, edits the same page together, and an admin decides who may open which world.

- **World access.** Table `workspace_members(workspace_id, user_id, role editor|viewer)` (migration #13; existing accounts were added to every world). `server/src/access.ts` checks every `/api/` request that reaches into a world once, in a global `onRequest` hook: the world comes from the path (`/api/workspaces/:ws/...`, or the row behind `/api/pages/:id`, `/api/maps/:id` and the other id routes). A non-member gets 404, a viewer gets 403 on writes. Owners reach every world. A global viewer account is read-only in every world. `GET /api/workspaces` lists only the worlds the account may open and adds `role`; the client makes `user.role` `viewer` while a viewer world is open (`account` keeps the real role). Deleting a world is owner only. Copy checks read access to the source worlds and write access to the target. Folder, page and zettel ids sent by a client must belong to the same world.
- **Admin dashboard.** `server/src/admin.ts` and `admin-ui.ts`: a second Fastify server on `ADMIN_PORT` (default 3001, bound to `ADMIN_HOST`, default 127.0.0.1) with its own account (`admins`, `admin_sessions`, cookie `dnd_admin`, `SameSite=Strict`), a strict CSP and no outside resources. It lists worlds with their members, adds and removes people with editor or viewer access, creates, renames and deletes worlds, creates accounts, changes account type, sets passwords, signs people out, and shows who is online and what they are editing. The Online tab is pushed, not polled: the dashboard server has an event stream (`GET /api/events`, server-sent events behind the admin login) that sends a data-less notice whenever someone connects, leaves, opens a page or loses access (`server/src/presence.ts`, called from `live.ts` and `collab.ts`; bursts within 200 ms become one notice). The page then asks for the overview again, and does so once more after a dropped stream comes back. On the other tabs only the count in the tab bar is refreshed, so a form being typed in is never redrawn. The first account is created from `ADMIN_PANEL_USER` and `ADMIN_PANEL_PASSWORD`; with neither it stays off. At least one owner account must remain.
- **Live editing.** Each open page has a room on the server (`server/src/collab.ts`) holding a Yjs document, reached by WebSocket at `/api/collab/:pageId` (same origin, session cookie, member of the world). The editor uses TipTap's Collaboration and CollaborationCaret extensions; cursors carry the person's name and colour. The shared document is stored in `page_docs` and written to `pages` (text, outline, links, todos, history, statistics) at most every 1.5 seconds while people type and when the last person leaves, through the same `applyContent` an editor save used. `server/src/ydoc.ts` converts between the stored TipTap JSON and the Yjs structure without a ProseMirror schema; the first open of a page seeds it from the stored JSON. Viewers see changes live but their edits are ignored. Content written by anything else (REST `PATCH` with `content`, restoring a version, relinking library terms, restoring a backup) drops the room and tells open editors to reload; todo changes from the Todos tab are applied to the live document instead.
- **Live stream.** `GET /api/live?ws=` (server-sent events, `server/src/live.ts`) tells each tab about changes by others: `refresh` after any write in the world (the client reloads its lists and the views that keep their own copy), `page-saved` with the derived page data, `presence` with who is online, `worlds` when an admin changed access. Requests carry `X-Client-Id` so a tab is not told about its own change.
- **Fields on special pages.** `PATCH /api/pages/:id` takes `propsPatch` (`data`, `portrait`, `type`) merged on the server, so two people editing different fields do not overwrite each other. Title and tags are still last write wins.
- **Restore.** Backup restore keeps accounts, memberships (pruned to worlds that exist) and admin accounts, and resets all rooms.
- **Tests.** `node scripts/smoke-multiuser.mjs <url> <user> <pass> <admin-url> <admin-user> <admin-pass>` (access, dashboard, live editing, live stream), `scripts/test-ydoc.ts` (conversion and merging).
- **Not covered.** Maps, the timeline and relations refresh their lists live but an open map view does not follow another person's edits to its items. Offline edits to a page are kept and merged while the tab stays open; a page opened while offline is read-only.

## Tabletop (phase 1, built)

What it does: the GM and the players share a battle scene. The GM makes scenes and tokens, players move the tokens they own, and everyone sees changes as they happen. The plan for everything beyond this is in `docs/VTT-ROADMAP.md`.

- **Where.** Sidebar, Play group: Tabletop (also "Open the tabletop" in the command list). One table per world. The owner account is the GM; accounts named in the table rules also run it; world editors are players; world viewers only watch.
- **Scenes.** A scene has a map image (a world upload, up to 25 MB; its size becomes the scene size), a grid (square, hexes with a pointy or flat top, or none), a cell size in pixels, what a cell is worth (5 ft by default, any unit) and a diagonal rule (every second diagonal counts double, every diagonal one cell, straight line, across then down). The GM looks at any scene; "Move players here" brings everyone along, and players always follow the table's scene.
- **Tokens.** Name, size in cells (half a cell to five), colour or picture, turn, hide, lock and who controls it. They snap to the grid while they are dragged. Players move and turn only the tokens they own (and not locked ones); hidden tokens are never sent to players unless they own them. The panel lists the tokens of the scene so they can be picked without the mouse. Keys: arrows nudge one cell, R turns, H hides, L locks, Delete removes (GM), F fits the scene, Esc clears the selection, Ctrl+A selects all.
- **Seeing and measuring.** Drag empty ground to move the view, scroll or pinch to zoom, shift-drag to select several. Dragging a token shows the distance it travelled. The ruler tool measures a line and shares it with the others. Alt+click (or holding still on a touch screen) pings; everyone sees the ring. Other people's pointers are shown by name when the table allows it.
- **Hit points, conditions, chat and dice (phase 2).** A token carries hit points (current, maximum, temporary), armor class and conditions in its `data`; the bar and condition pips are drawn on the map and a token at zero hit points is crossed out. Damage wears down temporary hit points first, healing stops at the maximum, hit points do not go below zero. The GM can hide a token's hit points and armor class from other players: the server then leaves them out of what it sends (owners and GMs still get them). The rules switch "Players change their own hit points and conditions" is on by default. Linking a page to a token (GM, "Link a page") takes its picture and, for a creature with a sheet, its hit points and armor class; the creature's sheet appears in the panel with a roll button on every check, save, skill, attack and damage (Shift for advantage, Ctrl for disadvantage).
- **Chat and dice.** A Chat tab with quick dice. The server rolls: `/roll 2d20kh1+5 stealth`, keep and drop (`kh kl dh dl`), exploding dice (`!`), `d%`, `adv` and `dis` after a roll, rolls inside talk with `[[1d8+3]]`. `/gmroll` is seen by the GMs only, `/w name text` is a whisper (not even the GM sees it), `/me` is an emote. The GM can speak as someone else. Spectators can talk but not roll. The last 100 visible messages come with the snapshot; messages are kept 90 days (`chat_messages`). Tests: `scripts/test-dice.ts`, `scripts/test-chat.ts`, `scripts/smoke-table.mjs`, `e2e/tests/tabletop.spec.ts`.
- **Walls, light and fog (phase 3).** The GM draws walls with the wall tool (click to place points, double-click or Enter to finish; points snap to half cells and to other walls' ends) in four kinds: wall, door, secret door (looks like a wall to players) and window (light and sight pass). Doors open and close with a click for the GM, and for players when the rules allow it. A scene can have **fog of war** and a **darkness** level (0 to 100 %). With fog on, a player sees what their own tokens see: walls block sight, and the area must be lit by the sky (darkness below 100 %), by a light source, or by the token's darkvision. What they have seen stays dimmed on the map; the explored area is stored per player (`scene_fog`) and the GM can reset it. A token has "Sees up to" (blank means as far as walls allow), "Darkvision", "Bright light" and "Dim light" in the scene's unit; hidden tokens still give light. Tokens in the dark or behind a wall are not drawn for players. The GM, and spectators, see the whole map. Walls are stored in `scene_walls`; the picture is computed in the browser (`web/src/tabletop/visibility.ts`, `fog.ts`).
- **Previewing as a player.** The GM can look at the scene the way a player or a single token sees it, so a map can be built and checked without a second account: a "See the scene as a player does" choice in the top bar (a player, all players, or "Through" any token). Fog, darkness, light, secret doors and hidden tokens then behave as they do for that viewer; what the preview explores is not remembered or saved. The button next to the choice leaves the preview.
- **Views and moving around.** The GM can save views of the map to come back to (kept in their browser, per scene), and "Bring everyone here" shows every other person on the scene the part of it the GM is looking at. Ctrl+Z puts back the tokens of a person's last drag (up to 30 drags). In the ruler tool, holding Shift while dragging keeps the measured part and carries on from where it ended, so a path around corners adds up.
- **Light and roofs.** A light can have a colour (a tint over what it reaches, in a scene with fog or darkness). An overhead tile fades over the tokens of the person looking, so what is under a roof can be seen; the GM's own view keeps the roof. "Players see through each other's tokens" in the table settings makes the party share sight, on the screens and in what the server sends.
- **Props, variants and item bonuses.** A prop (tile) can be flipped like a mirror. A token can keep up to eight picture variants of the world's files and "Shuffle the picture" picks one at random (a crowd that does not all look alike). An item on a sheet can add to armor class while equipped ("Equipped items add 3 to armor class, for 15 in all"). On tablets (wide, touch) the buttons and chips of the table are bigger.
- **Small table conveniences.** A macro whose name has a slash (`Spells/Bless`) is kept in a folder button (`Spells`) in the macro bar. Items on a character sheet can have charges (a wand or staff): a number in all and bubbles for the spent ones. "Panel on the left (for left-handed use)" in the Table panel moves the side panel to the left of the map (kept in the browser).
- **Session replay.** The table notes where tokens are put, moved and taken away, their hit point changes and the scenes shown (kept for a month). "Replay the last session" in the Table panel (GM account) plays the latest session back: tokens moving over the map, a position slider, and what was said beside it.
- **Asset library.** "Asset library" in the Scene panel (GM account) lists every picture and sound uploaded to the world with its size and tags. It can be searched by name or tag and filtered to pictures or sounds, several files can be added at once, a file can be tagged (lower case, up to 12 tags) or deleted, and a picture can be used as the scene's map, a token or a prop, a sound as a jukebox track. A world keeps at most 1024 MB of files (set `UPLOAD_QUOTA_MB` to change it); an upload past that is refused with a message pointing at the library. Routes: `GET /api/workspaces/:ws/uploads`, `PATCH` and `DELETE /api/uploads/:id`.
- **People at the table.** In the Table panel the GM can Mute a player (they can still read, but cannot talk or roll in chat), Kick them (they are disconnected and have to open the table again) or Ban them (disconnected, and they cannot come back until the GM lets them in again from the banned list; GMs cannot be muted, kicked or banned). "Ready check" shows everyone a banner where players answer "I am ready" or "Not yet" and everyone sees who has answered how, until the GM ends it.
- **Jukebox streams and scenes.** A track can also be a stream: "Add a stream" takes an https address of a sound file or an audio stream. Each track can belong to a scene: it starts by itself when that scene is shown to the table and stops when another scene with its own sound is. (Sound that fades with distance from a point on the map is not built.)
- **Chat.** `/as Name text` (or `/as "Old Mara" text`) lets the GM speak as someone else; `/ooc text` is out of character talk, shown quieter. A damage or healing roll in the chat (a label with "damage" or "healing") has an "Apply" button that puts it on the selected tokens, with the damage type from the label.
- **Importing and exporting characters.** On a person page without a sheet, "Import a character" reads a Chronicle character file, a Foundry VTT D&D 5e actor (JSON), the JSON of a D&D Beyond character or the attributes of a Roll20 character, and fills the sheet as far as the file says the same things (scores, hit points, armor class, classes and levels, species, background, proficiencies, items with weight and attunement, features, spells as a list, money; Roll20 carries less). "Export this character" saves a Chronicle character file. Pure parts: `web/src/lib/importers.ts`, test `scripts/test-importers.ts`.
- **More combat.** The one whose turn it is can Wait: they go after the next one in the order and the turn passes on. "Lair actions" (and "Another line") put a line that is not a creature in the order, at initiative 20 or another number. A combatant can have a legendary action tracker (three pips, back when their turn begins) and a reminder that is said when their turn begins (to the GM only for a hidden one). An effect can last "until the end of their next turn": it starts counting when that turn begins and is over when it ends. Creatures staged from an encounter keep their group: hidden groups wait in a list where the GM reveals one group at a time, or reveals it and puts it in the fight (more of them are staged the same way, which is how reinforcements arrive). When the GM ends a fight they are told what was put out of it and what it is worth in experience.
- **More drawing.** The draw tool also makes arrows and closed shapes (click the corners, double-click or Enter to close; a fill can be partly see-through), and "Fades away" makes a mark that goes by itself after a few seconds, for pointing something out. A drawing can be dragged elsewhere with the Select tool (your own; the GM's any). A spell area now also colours the grid squares it covers (the middle of the square inside, as the rules count them). **Pins:** the GM's Pin tool puts a labelled note on the map, optionally opening a Chronicle page when clicked, and optionally only for the GM. Alt+Shift+click (GM) pings a place and brings everyone to look at it.
- **More walls and light.** With the wall tool the GM can draw Lines or a Rectangle (four walls in one drag), and the kinds now include One-way: its arrow points to the side that can see through it, and from the other side it blocks the view (lights treat it as a wall). Ctrl-click on a door locks or unlocks it: a locked door is shut and players cannot open it. "Show area" lets the GM drag a rectangle that the players see as if their tokens had seen it (tokens in it are sent too; green outlines mark it for the GM) and "Hide area" takes one back. A token can have Blindsight and Truesight next to Darkvision (all three see in the dark within their reach), and a light can flicker or pulse (it moves the colour tint over what it reaches). A terrain wall that blocks only movement is not built, because movement is not enforced on the table.
- **Token looks.** The GM can give a token a shape (round, square, hexagon), a border colour, a tint, a flipped picture, a hidden name, a height (shown as an arrow and a number) and a coloured aura of a radius in scene units. Up to three extra bars (mana, charges, ammunition) sit under the hit points, edited by the GM. A marker of your own can be added to any token next to the condition chips. Tokens can carry action buttons (a name and a few chat lines, run like a macro, with `@{token|name}` for the token's name) that anyone who sees the token can press. Ctrl+C and Ctrl+V copy the selected tokens one cell down and across. "Roll hit points" rolls a linked sheet's hit point formula for one token, or for each selected token, so a mob of the same monster is not all the same. In combat the order shows how far the token whose turn it is has moved this turn.
- **Scene tools.** A scene has a folder (the scene list shows "Folder › Name" and sorts by it), notes only the GM is sent, a grid colour and strength, and an ambient colour laid over the whole scene. "Duplicate this scene" copies its walls, tiles, tokens and editor map. "Send players here" sends chosen players to look at a scene while the rest of the table stays where it is (the party splits); they come back to the table's scene when they reconnect.
- **Map editor.** In the Scene panel, "Open the map editor" opens a full-screen editor for the scene (GM account). A map is a grid of floor cells (5 to 100 cells each way) drawn with a rectangular Room tool and a Corridor tool (width 1 to 6), an Erase tool, Doors on the edges of cells, Props (table, pillar, chest, altar, statue, bed, barrel, stairs, rug, fire pit, turned in quarters with R or the Turn button), and Lights with a radius and a colour. Walls are never drawn by hand: they are worked out from where the floor ends (runs joined into single lines), so the picture and the walls cannot disagree, and a door on an edge splits its wall. Four looks (stone, cave, wooden hall, ice), undo and redo, zoom. "Make the scene" draws the picture at 70 pixels a cell, sets it as the scene's map with a 5 ft square grid, replaces the scene's walls and doors with the ones the map makes and the lights the editor placed before with new hidden light tokens, and keeps the map (a `map_docs` row) so it opens again as it was left; tokens stay where they are. Pure parts: `web/src/tabletop/mapdoc.ts` (test `scripts/test-mapdoc.ts`) and the picture in `mapRender.ts`; routes `/api/workspaces/:ws/scenes/:scene/map-doc` (checked in `scripts/smoke-table.mjs`).
Not yet in the editor: round rooms and caves drawn freehand, rotated or diagonal walls, floor textures other than the four looks, windows and secret doors, props as pictures, and several levels.
- **Universal VTT.** In the Scene panel, "Import a Universal VTT map" makes a new scene from a .dd2vtt or .uvtt file (Dungeondraft, DungeonAlchemist and others): the picture is uploaded, the grid and size are set, lines become walls, portals become doors and each light becomes a hidden light token, with its colour. "Export as Universal VTT" saves the current scene the same way (walls and secret doors as lines, doors as portals, lights by range), so it can go to Foundry or Roll20. Windows and one-way walls have no equivalent in the format. Pure conversion: `web/src/tabletop/uvtt.ts`, test `scripts/test-uvtt.ts`.
- **Editing walls.** With the wall tool, dragging the end of a wall moves it, and every wall that ends at the same point moves with it (it snaps to the grid or to another wall's end); a click on an end, without dragging, starts a new wall from there.
- **Fog hides tokens on the server.** On a scene with fog or darkness a player is only sent the tokens their own tokens can see: in the line of sight (walls block it) and lit. A token that is out of sight, or hidden, is not sent at all, so its place cannot be read from a modified browser. The server recomputes the view when a token moves, a door opens, a light changes or the scene settings change. Still sent to everyone: the walls, the lights and the order of play. Spectators are not filtered.
- **Combat (phase 5, first part).** The Combat tab keeps the order of play. The GM adds the selected tokens or everyone on the scene and rolls initiative for those without one (1d20 plus the initiative on the creature's sheet, else its Dexterity modifier; the roll shows in chat, privately for hidden combatants). Players can type the initiative of their own tokens. Start combat begins round 1 with the highest; Next turn moves on and counts the round when the order wraps; the person who owns the token whose turn it is can end their own turn. The token whose turn it is has a blue ring on the map. A combatant can be marked out of the fight (skipped), hidden (players never see it or its turn) or removed; deleting its token removes it. One combat per world (`table_state.combat`); rules in `server/src/combat.ts`, tests `scripts/test-combat.ts`.
- **Encounters (phase 5, second part).** The GM's Encounters tab plans a fight: creatures from the world's pages (a creature needs a stat block with a challenge rating; import it from the Library first), how many of each, and the party's levels. Difficulty follows the 5e 2014 method: the creatures' XP times a multiplier for how many there are (one step up for a party under three, one down over five) against the party's easy, medium, hard and deadly thresholds (`web/src/tabletop/encounter.ts`, tested by `scripts/test-encounter.ts`). The 2024 XP budget is not included. "Place on this scene" puts the creatures on the scene (hidden unless unticked), named with a number, linked to their page, with hit points and armor class from the sheet, hit points kept from players and the picture from the page portrait; "Place and roll initiative" also adds them to the order of play. Encounters are stored per world (`encounters`, routes under `/api/workspaces/:ws/encounters` and `/api/encounters/:id`, owner account only, so players never see them) and are not copied or exported with a world. Tests: `scripts/smoke-table.mjs`, `e2e/tests/tabletop.spec.ts`.
- **Drawing (phase 4, first part).** The pencil in the toolbar draws on the map for everyone: a pen, a line, a box, a circle (optionally filled) or text, in seven colours and any width. The eraser removes the drawing under the pointer (players only their own; the GM any, and walls). The GM can draw "GM only" (shown faded to the GM, never sent to players) and clear all drawings of a scene. Drawings are stored in `drawings` and arrive as one finished shape, not stroke by stroke. Players can draw unless the rules say otherwise. Drawings sit between the grid and the tokens.
- **Tiles and layers (phase 4, second part).** The GM's Scene tab has "Add a tile": a picture (a world upload) laid on the scene as furniture, rubble, a roof. A new tile is about three cells across. Click a tile on the map with the select tool to move it (it snaps to half cells); the Token tab then edits it: layer, width, height, rotation, lock, hide and order. Three layers: **below the tokens**, **above the tokens** (roofs, treetops; still below fog) and **GM only** (never sent to players, shown faded to the GM). A hidden tile is also never sent to players. Tiles are stored in `scene_tiles` and, like drawings, are GM-only to change. Keys: Delete removes the selected tile.
- **Spell areas (templates).** The draw tool's Cone, Ray, Burst and Cube place the 5e shapes from an origin to the far end, snapped to whole cells, with the length in the scene's unit: a cone is as wide at the far end as it is long, a ray is one cell wide, a burst is a circle around its centre, a cube is a square with the origin in the middle of one side. They are drawings, so everyone sees them, the owner or the GM removes them with the eraser, and "Clear drawings" clears them. The cells they cover are not highlighted or counted yet.
- **On a phone.** Below 900 px the table is a phone layout: the map fills the screen, a bottom bar switches between **Map**, **Me** (your own token with its hit points, conditions and sheet card; it picks your token for you), **Combat** (the order of play and "End my turn"), **Chat** (dice buttons and chat) and **More** (the table rules, and for the GM scene, tiles and encounters). Everything but Map opens as a sheet over the lower part of the screen, so the map stays where it was. A strip above the bar shows the hit points of a token you own with Damage and Heal buttons, so the most common thing at a table needs no menu. Pinch zooms, one finger moves the view or a token you own, holding still on empty ground pings, buttons are at least 40 px. The page can be added to the home screen (the manifest was already there); there are still no PNG icons, so some browsers will not offer to install it. Test: `e2e/tests/mobile.spec.ts`.
- **Rules of the table.** The GM switches on or off: players move their own tokens, add tokens, ping, share their ruler, and see each other's pointers.
- **Technical.** WebSocket `/api/table/:world` (`server/src/table.ts`, rules in `tabletop.ts`), the browser side in `web/src/tabletop/` (PixiJS scene in `engine.ts`, grid maths in `grid.ts`, live state in `state.ts`) and `web/src/components/Tabletop.tsx`. Tables `scenes`, `tokens`, `table_state` (backed up and restored with the rest). Not carried by world copy or export yet.
- **Tests.** `scripts/smoke-table.mjs` (who sees and may do what), `scripts/test-grid.ts` (snapping and distances), `e2e/tests/tabletop.spec.ts`.
- **Not done yet.** Occlusion of a token that walks under an overhead tile, covered-cell highlighting for spell areas, user-defined layers, live strokes while someone is still drawing, undo, conditions that end on their own at the turn, 2024 XP budgets, loot and XP summary after a fight.

## Rules automation (5e, first step, built)
The GM can let the table apply some rules. They are on the Table panel under "Rules the table applies for you", all off until chosen, and work on tokens linked to a sheet.
- **Damage types.** Damage can carry a type. Resistance halves (rounded down), vulnerability doubles, immunity stops it, and resistance with vulnerability to the same type cancel out. An entry with a condition ("slashing from nonmagical attacks") is not applied, because the table cannot tell if a weapon is magical. What happened is said in chat; for a hidden token or one with private hit points only the GM sees it.
- **Concentration.** A token with the Concentrating condition that is hurt makes a Constitution save against DC 10 or half the damage; failing, or dropping to 0, ends the condition. The roll is shown in chat.
- **Death saves.** A character at 0 hit points becomes Unconscious, gets a Death save button (a natural 20 brings them back with 1 hit point, a natural 1 counts twice, three failures kill, three successes make them stable), and is back on their feet when healed.
- **Rests**, always available on a linked character: a short rest spends hit dice (largest first) and readies "after a rest" features, a long rest restores hit points, spell slots, uses, half the hit dice and clears death saves.
- **Spell slots and uses** show on the table card as pips and a Use button, written back to the sheet. Pure rules: `server/src/rules5e.ts`, test `scripts/test-rules5e.ts`.
- **Attacks on targets.** A fourth switch. On the table card a feature with a to-hit bonus or a saving throw gets a Target choice and a "Roll on target" button (Shift for advantage, Ctrl for disadvantage). The server rolls the attack against the target's armor class (a natural 20 hits and doubles the dice, a natural 1 misses), or the target's saving throw against the DC (half damage when the text says "half as much"), rolls the damage, applies it through the same damage rules and reports it in chat. A target without armor class is only rolled against. Targets at a secret token are reported to the GM and the attacker only.
- **Active effects.** A token carries spell effects (presets for Bless, Bane, Shield of Faith, Haste, or a custom name with rounds and an armor class bonus). An effect can add to armor class, attack rolls ("+1d4") and saving throws, and these reach the automated attack and saving rolls and concentration saves. A duration is in rounds: it goes down when a new round of the order of play begins and the effect is said to end at 0. An effect with a duration can be tied to the caster's concentration and ends when the caster stops. Players cannot see an armor class bonus on a token whose hit points are private. Pure rules: `server/src/effects.ts`.
- **Level up.** On a character sheet, "Level up" asks for the class (or a new one), takes the average hit die or a roll, adds the Constitution modifier (at least 1 hit point), adds a hit die, recalculates spell slots (one casting class uses its own table, several add up as the multiclass rules say; spent slots stay spent) and says when the proficiency bonus or an ability score improvement comes. If the world has a page titled like the class that was imported from the library, the features it lists for the new level are offered and added to the traits. A class whose hit die is not known asks for it. Pure rules: `web/src/lib/levelup.ts`, test `scripts/test-levelup.ts`.
- **Carrying and attunement.** Items have a weight and an attuned box. The sheet shows what is carried against 15 pounds per point of Strength, with the variant steps (encumbered over 5 times Strength, heavily over 10), and how many items the character is attuned to out of 3.
- **Reactions.** The order of play has a reaction button per combatant, for the GM and the owner, spent by hand and ready again when their turn begins.
- **Areas as targets.** A spell area drawn on the map (cone, ray, burst, cube) can be chosen as the target of an attack or save: everyone inside it is rolled against (`inTemplate` in `web/src/tabletop/grid.ts`).
- **Down characters.** With death saves switched on, damage to a character already at 0 hit points is a failed death save, and as much as their maximum kills them outright.
- **Pact Magic.** A warlock's slots (count and level by warlock level) are put in the slots of the sheet on level up, added to any other casting.
- **Pathfinder 2e actions.** In a Pathfinder world the order of play shows three action pips per combatant, spent by hand by the GM or the owner and back when their turn begins.
- **Opportunity attacks.** In combat, when the token whose turn it is walks out of the reach of a creature on the other side (a player's token against creatures without an owner, or the reverse) that still has its reaction, the table says so and the GM and that creature's owner get a banner with "Attack" and "Let it go". Attack rolls the first melee attack on the creature's sheet against the mover and spends the reaction (needs attacks switched on under automation). A creature with the condition Disengaged, or a hidden mover, does not draw one.
- **Drag ruler.** A token has a walking speed (a Speed field in its stats, filled from the sheet when an encounter is placed). While dragging it, the ruler shows the distance against what is left of the speed, in green within it, yellow up to a dash (double) and red beyond. In combat what the token already walked this turn is taken off. Difficult terrain is on the backlog, far back.
- **Roll templates.** `/card Title | Label: text and [[1d20+5]] | Damage: [[1d8+3]] slashing` posts a titled card of lines in the chat, each line with an optional label and any rolls inside (`dc 15` after a roll shows its degree). The Roll20 form `&{template:default} {{name=Title}} {{Hit=[[1d20+5]]}}` works too. Up to 12 lines; a macro button can hold a card line, so an attack or spell card is one click (`parseCard` in `server/src/chat.ts`).
- **Level up choices.** The level up panel asks for a subclass at the level the class chooses it (suggestions from the basic rules, any name can be typed; an Eldritch Knight or Arcane Trickster gets spell slots), and at an ability score improvement level (fighters and rogues have extra ones) lets the player spend 2 points, at most 2 on one score and 20 at most, or take a feat by name instead. A higher Constitution modifier adds hit points for every level. Features of the subclass still come from a class page of the world.
- **Cones of light, terrain walls and night vision.** A token's light has an Angle (degrees across, 360 is a full circle) and a direction (Light faces, degrees clockwise from the top), so a lantern shutter or a spotlight lights a wedge; walls still stop it. A new wall kind, Terrain (a hill, a hedge), is seen past once but two in a row end the view (players and the server's hiding of tokens agree on it). What darkvision shows in the dark is washed out and cool-coloured. Light and sight already pass through windows, which only block walking.
- **Named layers.** In the Scene panel the GM adds up to 12 named layers (Furniture, Secrets, an upper floor) and puts tiles on them from the tile's panel (Named layer). Each layer can be handed to the players or kept GM only (its tiles are then not sent to players at all), locked (its tiles cannot be moved), and hidden on the GM's own screen only. This is on top of the three stacking layers (below the tokens, above, GM only). Tokens are not on named layers.

## Macros and handouts (built)
- **Macros.** Saved chat lines in the chat panel, one button each. Each person keeps their own (up to 100 per world); the owner account can share one with everyone. A macro is several lines, each sent as its own chat message (at most 10 per run). `?{Question|default}` asks when it runs (`?{Stance|Careful|Bold}` lists the options); `@{selected|name}` fills in the selected token: name, hp, maxhp, ac, and from its sheet level, prof, str to cha and str_mod to cha_mod. A reference that cannot be filled stops the macro with a message. Spectators have none. Routes: `/api/workspaces/:ws/macros`, `/api/macros/:id` (smoke test `scripts/smoke-macros.mjs`); pure parts in `web/src/lib/macro.ts`, test `scripts/test-macro.ts`.
- **Handouts.** A Handouts tab. The GM writes a title, plain text and an optional uploaded image, and chooses who can read it: everyone, chosen players, or nobody. When it is revealed it opens on the readers' screens (once per person) and stays in their list; "Again" opens it for everyone who can read it. Players are never told who else can read a handout, and a handout that is not revealed to someone is never sent to them. They live in the `handouts` table and travel over the table channel (`handout.save`, `.delete`, `.reveal`, `.show`). Text is shown as plain text so it cannot run anything.
- **Roll tables.** A "Tables and decks" tab. The GM writes a table as one entry per line; a leading `3: ` makes an entry three times as likely, and `[[2d6]]` inside an entry is rolled when it comes up. Anyone but a spectator rolls with a button or `/table name` (a name that starts the same is enough); the roll is shown as a die as big as the total weight with the entry after it. A secret table can only be rolled by the GM, the players are not told it exists, and the GM's roll of it is shown to GMs only. Players never receive the entries of a table.
- **Card decks.** The GM writes a deck as one card per line, `Name | what it says`, with `3x ` for copies. The server holds where every card is. A player draws to their hand (nobody else sees which cards, only how many are held) or face up (said in chat, then discarded), and plays a card from their hand (said in chat, onto the face-up discard pile). When the pile runs out the discard pile is shuffled back in; only the GM shuffles everything back, and changing a deck's cards deals it out again. Pure rules: `server/src/tables.ts`, test `scripts/test-tables.ts`.
- **Jukebox.** In the "Tables and decks" tab the GM adds sound files of the world (MP3, OGG, WAV, WebM, M4A or AAC, up to 25 MB; kept in the world's uploads like images), names them and plays or stops each; several can play together, so a looping rain can run under a battle theme. Everyone hears what is on, with their own volume and mute (kept in their browser), and the first sound needs one click because browsers hold sound back. What is playing is not kept over a server restart. New people who join are told what is on.
- **Handouts from pages and a session recap.** "From a page" on the Handouts tab fills a new handout with the title, the words and the portrait of a page, to edit before saving. "Draft a recap page" in the chat panel makes a page from the chat of the latest session (the newest messages back to a gap of six hours), one line for each thing said, done or rolled, with whispers and secret rolls left out. Pure rules: `server/src/recap.ts`, test `scripts/test-recap.ts`.
- **Triggers.** Event hooks without scripts, for the GM only (a Triggers section in the Scene panel; on the map an orange circle marks a place). A trigger waits for one of three events: a token that belongs to a player comes into a place (a centre taken from the selected token, with a radius in cells), a new round of combat begins, or a token goes down to 0 hit points. It then says something at the table (`{name}` is the token's name), shows a handout to everyone, or starts a jukebox track. It can fire only the first time (and be armed again with the reset button) and can be limited to one scene. Players are never sent the list of triggers. Arbitrary scripts are not supported on purpose: they cannot be sandboxed on a small self-hosted server.
- **Weather.** A scene can have rain or snow falling over the screen for everyone (the Weather choice in the Scene panel).
- **For people who cannot see colours or the screen.** Conditions on a token carry their first letter, tokens can be moved with the arrow keys, and the order of play announces the round and whose turn it is.
Not yet: arbitrary GM scripts.

## System packs (built, first version)
A system pack is one JSON file (`"format": "chronicle-system"`) that a world can install and play by, so a rules system can be shared and other games can be started from the three built-in ones. It builds on one engine (`base`: 5e 2014, 5e 2024 or Pathfinder 2e), which still decides how rolls, difficulty, degrees of success and the sheets work, and changes what is shown and offered:
- **abilities**: a name and a short form for each of the six ability slots (the sheets and the table card show them);
- **conditions** and **damage types**: the lists on a token (and the damage type of a hit; resistance, vulnerability and immunity match the pack's own types);
- **initiative**: the dice a token without a sheet rolls (1d20, 1d10, 2d6 and so on);
- **grid**: the unit, the size of a cell and the grid type new scenes start with;
- **content**: roll tables, card decks and macros, added to the world (macros shared with everyone) if the owner chooses to when installing.
Only the owner account installs, switches on or removes a pack (Settings, Worlds, System packs); everyone in the world can read and export them. Choosing a built-in rule set again leaves the pack, and removing the pack in use does too. The three built-in systems are packs as well (an "Export a built-in system" choice gives a file to start from). Unknown fields are refused with a message naming the field. Pure parts: `server/src/pack.ts` (test `scripts/test-pack.ts`) and `web/src/lib/systems.ts` (test `scripts/test-systems.ts`); routes under `/api/workspaces/:ws/packs` (smoke test `scripts/smoke-packs.mjs`).
Not yet: a pack that defines its own sheet fields, skills and derived numbers, roll definitions, rest rules and difficulty rules, so a game that is not built on one of the three engines (Call of Cthulhu, Shadowrun, Savage Worlds and so on) needs engine work first.

## Invite links (built)

What it does: the owner makes a link for a world and sends it to the players. Whoever opens it can make an account (or sign in with one they have) and is let into that one world as a player or a spectator. Accounts made by the admin dashboard and the owner's Accounts list keep working as before.

- **Where.** Settings, Worlds, owner only: "Let people join this world with an invite link" (per world, off by default; `workspaces.settings.invites`), then a role (player who can write, or spectator who can only read), how long the link works (1, 7, 30 days or no end) and how many people it lets in (1, 5, 20 or any number). "Create link" shows the link once with a Copy button. The list shows each link's role, how many joined, when it ends and its state (open, used up, expired, revoked) with a Close button. Switching the world's setting off closes every link at once.
- **The page.** `/join/<token>` needs no sign in. It says which world and role the link is for and offers "Make an account" (a name of at least 2 characters, a password of at least 8, entered twice) or "I have an account". After joining, the person is signed in and the app opens on the world. A new account gets the invite's role as its account type and is a member of that world only. Someone who is a member already is simply signed in and does not use the link up. The owner account cannot use a link (it already reaches every world).
- **Security.** The token is 32 random bytes; only its SHA-256 is stored, so a link cannot be shown again (make another). All the reasons a link can be invalid (unknown, closed, expired, used up, invites switched off, world deleted) give the same answer, so the page does not tell a guesser which. The public routes (`GET /api/public/invite/:token`, `POST /api/public/invite/:token/join`) reveal only the world's name and the role; they are rate limited (20 and 8 a minute per address). Joining with an existing account checks the password with the same hash and does the work even for unknown names, like login. Only the owner account can make, list or close links.
- **Data and API.** Table `invites`; `GET|POST /api/workspaces/:ws/invites` and `DELETE /api/invites/:id` (owner only, the delete closes the link and keeps its history). Backup restore resets links to the backup's.
- **Not done yet.** Showing who joined with which link, a link per person with a name on it, an e-mail invitation, links in the admin dashboard.
- **Tests.** `node scripts/smoke-invites.mjs <url> gm <pass>` and `e2e/tests/settings.spec.ts` (invites).

## Page history (built)

What it does: every edit to a page is recorded with who made it and when, and any earlier version can be restored in full. The clock button on a page opens the history.

- **What an entry holds.** The state of the page after an edit: title, text, special-page fields and portrait (`props`), icon, aliases and tags. Table `page_versions` gained `author_id`, `author_name`, `props`, `meta`, `reason`, `restored_from` (migration #14). The author is stored as a name too, so an entry survives a deleted account. Entries from before this change hold text only and show as "Earlier version"; restoring one keeps the page's current fields.
- **When an entry is made.** `recordRevision` in `server/src/pages.ts` runs after every change to a page: `PATCH /api/pages/:id`, a live editing save (`collab.ts` credits the last person who changed the document), a todo change, relinking library terms. Edits by the same person within 5 minutes of the entry's start fold into that entry, so a restore point exists for every edit without storing every keystroke. An edit by someone else always starts a new entry. A change that leaves the page identical adds nothing. The first change to a page with no history also keeps its starting state (no author).
- **Kept forever.** No entry is ever thinned or deleted, except with its page.
- **Restore.** `POST /api/versions/:vid/restore` (editors) puts back title, text, fields, portrait, icon, aliases and tags. The folder is left where it is. What was on the page just before is recorded first, and the restore itself becomes an entry by the person who did it, marked with the date it restored. Nothing is lost, so a restore can be undone by restoring an entry before it. People editing the page live are told to reload.
- **Not covered.** History is not copied to another world or exported, as before. Two people typing in the same few seconds produce one entry credited to whoever changed the page last.
- **Tests.** `node scripts/smoke-history.mjs <url> <user> <pass>`.

## Look and navigation (built)

What it does: a calmer, easier to read shell. No data or API changed.

- **Type.** Titles and headings (page title, editor headings, view titles, the world name) use a book serif; body text stays on the reading font chosen in Settings. `--font-display` is set in `fonts.ts`: a book serif by default, the user's reading font when they picked one. Only fonts that ship with the OS are used, so the app still works offline.
- **Contrast.** The muted text colour of the light themes was darkened to reach 4.5:1 on its background. Small uppercase labels (sidebar and section headings) became sentence case.
- **Sidebar.** A world header at the top shows the current world and opens a menu to switch worlds, go Home or create a world (before, switching worlds was only in Settings and the command palette). The twelve views are grouped by use (Zettelkasten, Sessions, Todos, Comments; Graph, Maps, Timeline, Relations; Library, Templates, Special pages, Stat block forms) and the open view is highlighted. The "New page" button no longer wraps onto two lines.
- **Home.** The most recently edited page leads as a large card, followed by the rest with how long ago they changed. Shortcuts for writing a page, capturing a thought and searching sit under the world name, and the zettel and todo counts link to their views.
- **Touch and keyboard.** Row actions stay visible on screens without hover, rows are 40 px tall on phones, every button, card and chip shows a focus ring, and animations are turned off for people who asked for reduced motion.
- **Tests.** `e2e/tests/shell.spec.ts` (`shell.home-actions`, `shell.world-switcher`).

- **Settings.** A menu on the left (a scrolling strip of tabs on phones) opens one page per group: Appearance (theme, fonts), Keyboard shortcuts, Worlds (switch, create, starter todo, export, delete), Sharing (publicly shared pages), Accounts and Backups (owner only), Desktop app (desktop app only) and My account (password, log out). Viewers see the same sections minus the owner ones. Nothing about storage changed. Test: `settings.sections` in `e2e/tests/settings.spec.ts`.

## Operations
- Password change: `POST /api/auth/password` (own), owner can set another user's.
- Docker: health check on `/api/health`, graceful shutdown on SIGTERM (WAL checkpoint), `/data` owned by uid 1000, compose uses a named volume. Session cookie `Secure` follows `req.protocol` (behind cloudflared it is https).
- Umbrel: community store files in `umbrel/` (amd64 only), image published by `.github/workflows/image.yml`. Not tested on a real Umbrel.

## Known limitations / things to watch
- Offline edits are not queued across reloads.
- The service worker is a stub (installability only).
- Deleting a folder moves its contents up a level rather than trashing them.
- Copying between worlds does not carry map pins, events or history (todos not checked). Templates and custom page types are not copied either (their pages become plain pages; stat block forms are matched by name).
- Viewers cannot share. `/todo` is unavailable in read-only mode.
- Title and tags of a page are last write wins when two people change them at the same moment.
- Only amd64 images; Linux and Mac Electron builds untested.
